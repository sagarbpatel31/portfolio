# Firmware Validation Needs a Failure-Signature Pipeline

A large validation campaign can produce thousands of failures while containing only a few distinct defects.

One broken initialization path may fail on every reboot. A single timing issue may surface through several downstream assertions. An environmental outage may make unrelated tests look defective. If every failed case becomes an independent ticket, triage volume grows faster than engineering understanding.

The answer is not aggressive deduplication. It is a failure-signature pipeline that groups results using stable technical facts while preserving the context needed to challenge the grouping.

## A Signature Answers One Narrow Question

A failure signature should answer:

> Is this result likely another observation of the same underlying failure mode?

It should not claim to know the final root cause. That conclusion usually requires deeper debugging.

This distinction matters. A useful signature can group failures by the first violated contract, component, error family, and execution stage without pretending that every member has already been proven identical.

## Build a Pipeline, Not a String Hash

Hashing an entire log rarely works. Volatile fields such as timestamps, addresses, counters, device order, and retry numbers make equivalent failures look different.

A better pipeline has four stages:

```text
raw artifacts
  -> normalized observations
  -> structured failure signature
  -> reviewable failure cluster
```

The raw artifacts remain immutable. Normalization extracts stable facts. The signature selects the facts that define likely equivalence. The cluster records every member and the confidence of the grouping.

Each stage should be versioned so an engineer can reproduce why two results were grouped.

## Start at the First Broken Contract

Downstream symptoms are often plentiful and misleading.

If device initialization fails, later tests may report missing telemetry, workload timeouts, health-check failures, and cleanup errors. Signatures built from the last visible assertion will split one defect into several clusters.

Prefer the earliest reliable boundary:

1. identify the last completed checkpoint
2. identify the first violated invariant
3. record the responsible validation stage
4. attach later symptoms as supporting context

This approach aligns signatures with system transitions instead of test-script wording.

## Use Structured Fields

A practical signature can include fields like these:

```yaml
schema_version: 3
stage: device_initialization
component: accelerator_2
contract: required_link_width
error_family: negotiated_below_minimum
reset_context: warm_reset
firmware_family: candidate_B
topology_class: dual_accelerator
```

Not every field belongs in the signature key. Some fields should remain context.

| Field type | Example | Treatment |
| --- | --- | --- |
| Stable identity | stage, component class, violated contract | include in the primary signature |
| Diagnostic context | firmware version, reset source, topology | retain and optionally use for sub-clustering |
| Volatile detail | timestamp, memory address, attempt ID | exclude from identity |
| Evidence locator | artifact URI, checkpoint offset | retain on each observation |

The goal is to ignore noise without discarding information.

## Separate Primary and Secondary Signatures

One signature granularity is rarely enough.

Use a primary signature for broad triage and a secondary signature for meaningful variants:

```text
primary:
  stage + component_class + violated_contract + error_family

secondary:
  primary + reset_context + topology_class + firmware_family
```

The primary view answers how many major failure families exist. The secondary view reveals whether a family is isolated to a particular transition, platform cohort, or release combination.

This hierarchy prevents both common mistakes:

- over-splitting one defect into hundreds of unique results
- over-merging different defects that happen to end with the same error code

## Test the Signature Logic

Signature code is production logic for the validation system. It needs tests of its own.

Build a labeled corpus with known examples:

- same defect with different timestamps and addresses
- different defects that share a final assertion
- one defect expressed through different test cases
- missing or truncated logs
- errors emitted before the expected checkpoint
- infrastructure failures that must not enter product-defect clusters

Measure false splits and false merges separately. A false split adds triage work. A false merge can hide a release-blocking defect inside a familiar cluster and is usually more dangerous.

## Preserve Unknowns

Do not force every result into a known cluster.

Create explicit states such as:

```text
matched
probable_match
new_signature
insufficient_evidence
infrastructure_failure
```

An `insufficient_evidence` result is not noise. It is feedback that capture failed before the signature could be formed. Track that rate as a validation-system quality metric.

A rising unknown rate after a harness change can reveal that logging, checkpointing, or artifact collection regressed even if the product behavior did not.

## Make Clusters Reviewable

Every cluster should expose:

- the normalized signature and schema version
- the earliest and latest observation
- affected firmware and hardware cohorts
- pass/fail history around each occurrence
- representative raw artifacts
- differences among cluster members
- current owner and disposition

Reviewers must be able to split a cluster, merge two clusters, or mark a signature rule as weak. Those decisions should become labeled examples for the next signature revision.

Automation should reduce repetitive sorting, not remove engineering judgment.

## Track Cluster Behavior Over Time

Counts alone are not enough. Useful cluster metrics include:

- first-seen and last-seen release
- occurrence rate by cohort
- recurrence after an apparent fix
- transition from intermittent to deterministic
- percentage of failures with complete evidence
- number of signature revisions affecting membership

A defect observed 100 times on one machine is different from a defect observed once across 100 machines. Cluster summaries should retain both frequency and distribution.

## Version the Signature Schema

When normalization or grouping rules change, historical comparisons can become misleading.

Record the schema version on every result and support offline reprocessing of retained artifacts. Then compare cluster membership before adopting a new rule:

```text
old clusters -> candidate normalization -> membership diff -> reviewer approval
```

A signature update that reduces cluster count is not automatically better. It may simply be merging too aggressively.

## Use Signatures in Release Decisions

A release dashboard should show more than total failures.

I want to see:

1. new signatures introduced by the candidate
2. known signatures whose occurrence rate increased
3. signatures crossing additional hardware or reset cohorts
4. failures without enough evidence to classify
5. fixed signatures that reappeared

These views turn a noisy red count into questions engineers can answer.

## The Operational Standard

Before trusting a failure-signature system, ask:

1. does it group by the first violated contract rather than the last symptom?
2. are volatile fields excluded without deleting their diagnostic value?
3. are false merges and false splits measured on a labeled corpus?
4. can reviewers inspect and revise every cluster decision?
5. can historical artifacts be reprocessed when the schema changes?

A pass/fail dashboard tells you how much red exists. A failure-signature pipeline tells you how many distinct problems the red probably represents, where they first diverged, and which evidence deserves attention first.
